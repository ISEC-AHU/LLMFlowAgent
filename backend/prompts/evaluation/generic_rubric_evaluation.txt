## Workflow Modeling Contract

* A node represents a selected executable API or observable business activity.
* Dependency Links represent the complete set of direct control-flow, invocation, or data prerequisites in the current DAG.
* Start and end events, gateways, branch labels, conditions, invisible transitions, and completion states may be implicit. Do not require them as standalone nodes unless they appear as registered executable operations in the supplied metadata.
* Parallel activities must not be ordered relative to one another unless the requirement explicitly imposes such an order. A subsequent join activity may instead depend directly on every required parallel predecessor.
* Node arguments describe inputs or data references; they do not add dependency edges beyond the authoritative Dependency Links list.

## Evaluation Rules

For each evaluation dimension:

1. Give a score from 1 to 5 and a concise reason of 20 to 50 words.
2. Base every conclusion on a verifiable fact in the requirement, DAG, or API metadata. Do not invent activities, dependencies, capabilities, or data types.
3. Identify the relevant nodes or links and quote or paraphrase the corresponding part of the requirement when it is relevant to the dimension.
4. Treat the authoritative Dependency Links list as the complete DAG. Never claim that a listed edge is missing and never treat an unlisted edge as present.
5. A DAG node whose name matches an available metadata entry is an assigned API or activity. Do not claim that such a node has no tool assignment.
6. Judge semantic suitability from the supplied name and capability description. Judge interface compatibility only when the relevant input and output metadata are available.
7. If metadata required by a criterion is unavailable, do not infer an error or deduct points solely for the missing metadata; evaluate the remaining verifiable aspects of that dimension.
8. Do not penalize the absence of an invented approval, confirmation, gateway, start, or end node when the requirement describes it only as a condition or implicit control event.
9. A dependency may encode a user-required control-flow prerequisite rather than direct data transfer. Do not mark that ordering incorrect solely because adjacent metadata input/output types differ.
10. Include at least one `evidence_checks` item. Record every DAG fact used in the reasoning as a check. Use only `node_exists`, `direct_edge_exists`, or `path_exists`, and set `observed` to the value you actually observe in the authoritative DAG.

## Scoring Reference

* **5**: The dimension is fully satisfied with no supported defect.
* **4**: The dimension is satisfied; only a minor supported issue exists.
* **3**: The dimension is partially satisfied; a supported issue has moderate impact.
* **2**: The dimension is largely unsatisfied; a supported issue significantly affects the workflow outcome.
* **1**: The dimension is unsatisfied because a supported critical defect prevents the intended outcome.
